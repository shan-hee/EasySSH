# 实例备份、设备同步与数据库迁移

日常跨端使用设备同步，整体恢复使用加密完整备份。完整备份采用 SQLite / PostgreSQL / MySQL 原生能力；Goose 负责数据库版本。通用 JSON 数据导出、预览和导入已移除，原有应用数据 JSON 文件不能在当前版本导入。当前开发基线已重新建立：服务端和桌面端各从 schema 1 开始，只接受新建空库，不提供此前版本的迁移或备份恢复兼容。重新安装时使用新的数据库和数据目录。

## 适用入口

| 目的 | 入口 | 内容 |
| --- | --- | --- |
| 故障恢复、升级前恢复点 | 系统设置 → 备份与恢复 → 完整备份；应急时使用 `maintenance backup` / `restore` | 原生数据库快照、数据目录、文件传输存储和根密钥 |
| Web 与桌面、多台桌面之间共享个人数据 | Web 账户设置 → 数据与同步；桌面顶部云图标旁的下拉菜单 → 同步设置 | 绑定远端账户，同步本人服务器配置、脚本，以及单独授权并开启的凭据、个人 AI 配置和 AI 历史 |
| 基线发布后的服务端增量升级 | 新程序启动时自动创建恢复点并迁移；`maintenance schema-upgrade` 为离线入口 | 升级成功并完成校验后才启动业务，详见下文 |
| 单版本回退 | 停机后 `maintenance schema-rollback` | 仅人工执行，不会自动降级 |
| 全新数据库 | 普通启动 | 按当前初始化基线创建空库 |

通过命令行执行完整备份前，必须先退出正常进程。系统内置入口复用原生快照与归档实现，无需手动停止服务。普通启动与维护共用操作系统文件锁，PostgreSQL/MySQL 还持有数据库会话级锁，避免另一台主机上的 EasySSH 同时写入同一个数据库。这也意味着同一数据库同时运行多个 EasySSH 进程不再受支持。外部 SQL 客户端不会遵守应用锁；维护期间不要用其他工具修改该数据库或文件目录。

命令由已构建的程序提供，不依赖 HTTP 服务是否能够启动。

## Telegram 聊天接入

导航中的「开放与自动化 → 聊天接入」独立管理 Telegram 机器人，模型配置沿用现有 AI 设置。创建连接时填写专用机器人的 Bot Token，选择服务器和权限模式；随后生成一次性绑定链接，在机器人私聊中绑定账号。链接有效期 10 分钟，重新生成会使旧链接失效。持有链接的账号会获得该连接配置的服务器权限。

第一版支持私聊文字、连续会话、`/new`、`/stop`、`/status`、`/help` 及任务审批。只读模式禁止 Shell 命令和文件变更；需审批模式沿用 Agent 的工具执行和外部上下文审批规则。审批与绑定身份、任务、操作内容及文件快照哈希关联，10 分钟后过期。群聊和附件尚未接入；飞书后端也已纳入初始化基线，见下文。网页的连接详情可打开每个绑定账号的当前 Agent 会话，历史会话在 AI 助手中查看。

服务端使用长轮询，不需要公网回调 URL，但必须能访问 `api.telegram.org`，可以使用服务进程的 `HTTPS_PROXY`。同一机器人只能由一个消费者接收消息；保存连接时会拒绝已配置 Webhook 的机器人。凭据按实例根密钥加密保存，不经管理接口返回。

收到消息后先提交轮询位置再交给 Agent：服务中断最多丢失一条消息，但不会重放可能已经改动服务器的操作。回复只在内存中排队，发送失败会短暂重试；重启或 Telegram 长时间不可达时回复可能丢失，结果以网页中的会话为准。

聊天接入初始化直接创建 `chat_connections`、`chat_bindings`、`chat_approvals` 和 `chat_received_events`，包含当前投递状态、审批和飞书标识字段。已废弃的会话映射表及收发队列表不再创建。

停用连接、变更配置或解除绑定会撤销旧执行上下文并请求停止相关任务。停止不能撤销已在远端完成的操作。完整备份恢复后，聊天连接默认停用，绑定和审批会被清除，必须重新启用并绑定；不会从旧备份恢复已有的聊天访问权限。

## 飞书长连接

飞书后端使用企业自建应用的长连接，接收私聊文字和审批卡片回调，不需要公网入站地址。需能访问 `open.feishu.cn` 及飞书返回的 WebSocket 服务地址。机器人权限、事件订阅和接口配置见 [API 文档](API.md#飞书聊天接入后端)。本次未增加前端配置页面。

初始化基线包含 `provider` / `app_id`、绑定的 `external_user_id` / `external_chat_id` 和事件去重表。Telegram Token 与飞书 App Secret 使用加密的 `token_cipher`；Telegram 使用数值机器人身份，飞书以 `(provider, app_id)` 唯一标识应用。重复事件不再次分发，记录保留 7 天，随连接删除而清理。完整备份恢复后的连接默认停用，需重新启用并绑定。

## SSH 跳板机

先添加并保存跳板机的登录凭据，再在目标服务器的「高级 → 跳板机」选择该服务器。目标地址由最后一跳访问和解析，跳板机的 SSH 服务需要允许 TCP 转发（`AllowTcpForwarding`，以及适用时的 `PermitOpen`）。终端、SFTP、监控、远程命令和 Docker 都使用相同的 SSH 路径。支持最多 16 跳，禁止自引用、循环引用和不存在的跳板机；被引用的跳板机需要先解除关联才能删除。

每一跳使用自己的已保存密码或密钥；目标服务器连接时填写的临时凭据不会发送给跳板机。交互式终端及 SFTP 认证窗口可以处理跳板机的交互认证；后台监控和命令执行需要无需交互的已保存凭据。每一跳分别校验主机密钥。分享访问同时要求对沿途跳板机具有访问授权，不会借目标服务器的授权访问未授权资源。

服务端和桌面端的 `00001_initial.sql` 已包含可空的 `jump_server_id`、索引和限制删除的自引用外键。无跳板机的连接使用 `NULL`，新建空库无需执行额外升级。此前的服务端 schema 5–11、桌面 schema 5–6 迁移链已经移除，旧实例需重新安装。

配置同步把跳板关系放在同一个连接配置内，凭据绑定也包含这条关系，避免同步后悄悄变成直连。桌面端须将目标与其全部跳板机加入同一同步空间；未加入的依赖会明确报错。无跳板的旧同步数据格式保持不变。旧版同步端不认识跳板字段，会拒绝这类配置；启用跳板机同步前须升级两端，不能让旧端丢弃该字段。修改跳板地址、身份、凭据或主机信任时，其依赖目标的连接版本会失效，后续文件和监控请求重新建连。

## 服务端启动自动迁移

服务端默认启用 `EASYSSH_AUTO_MIGRATE=on`。更新程序并重新启动时，在现有文件锁和数据库会话锁内读取 Goose 版本；旧实例必须先停止，HTTP 和后台任务均在迁移及校验通过后才启动。当前服务端 schema 为 2；从 schema 1 升级时执行 `00002_remove_csrf_trusted_origins.sql`，删除废弃的 `security_config.csrf_trusted_origins` 列和旧来源列表。回滚只恢复可空字段，不恢复旧值；需要旧值时使用升级前恢复点。SQLite/PostgreSQL 在事务内迁移；MySQL DDL 隐式提交，中断时按下文恢复流程处理。不使用 GORM AutoMigrate，不自动下载新程序，桌面端独立管理自己的版本。

| 数据库状态 | 行为 |
| --- | --- |
| 空库 | 初始化当前 schema |
| 当前版本，且无未完成的迁移记录 | 检查实际表和字段后启动，不重复创建恢复点；结构不匹配则拒绝启动 |
| 支持的旧版本 | 预检 → 加密恢复点 → 逐版迁移 → 校验 → 开放业务 |
| 高于程序版本 | 拒绝启动，要求使用匹配程序；不自动降级 |
| 非空库无版本记录、过旧版本、迁移路径不完整 | 拒绝猜测版本或覆盖结构 |
| 当前版本，但迁移记录仍未完成 | 验证原恢复点并完成校验，不能仅凭版本号放行 |

配置项：

- `EASYSSH_AUTO_MIGRATE=off`：应急关闭启动自动迁移；旧库或待校验的迁移仍会阻止启动。离线 `maintenance schema-upgrade` 明确执行升级，不受此关闭开关限制。
- `EASYSSH_MIGRATION_TIMEOUT=30m`：预检、快照、迁移和校验的总时间上限，支持 `1m` 至 `24h`。启动器通过认证的本地通道接收每 10 秒一次的阶段心跳；45 秒失去心跳或超过总上限即失败，心跳不会无限延长总上限。迁移完成后重新给予普通启动 90 秒。
- `EASYSSH_BACKUP_DIR`：复用现有备份目录；升级恢复点写入其 `migrations/` 子目录。默认位于数据目录旁的 `backups/`，应持久化保存。
- Compose 的 `EASYSSH_HEALTH_START_PERIOD=32m`：覆盖 30 分钟迁移及后续启动；增加迁移超时也要同步增加健康检查启动宽限。健康检查成功即可提前就绪，不会固定等待 32 分钟。直接 `docker run` 部署使用镜像默认的 32 分钟，可用 Docker 的 `--health-start-period` 调整。外部编排器的启动探针也要采用相同原则；Docker 本身不会仅因 unhealthy 自动重启容器。

### 恢复点与升级检查

恢复点复用原生数据库快照和 age 加密归档，使用实例根密钥经过 HMAC-SHA256 域隔离派生的密码，无需交互。归档包含 `database.dump`、加密封装内的 `root.key`、`upgrade.json` 和 manifest（数据库类型、原数据目录、源 schema、应用/数据库版本及文件校验和）。它的 profile 为 `server-migration`，与完整实例备份分开，不能通过普通完整备份恢复入口启用。

当前迁移只修改数据库，恢复点不复制传输文件、部署 `.env` 或外部数据库连接密码。原数据目录、传输存储和部署配置必须保留；未来若迁移修改文件，必须先扩展恢复范围。**解密仍需要外部保存的原实例根密钥**；归档内的密钥不能解决外部密钥丢失的问题，独立密码完整备份继续用于灾备。

归档先写临时文件并刷盘，再发布最终文件；随后解密校验所有文件。SQLite 还以只读连接检查快照实际 schema 与完整性。失败时不会执行升级 SQL。恢复点和最终结果报告不会自动清理；管理员可在确认升级稳定且另有灾备后清理旧成功记录，未完成迁移依赖的恢复点必须保留。失败重启复用同一恢复点和暂存路径，不不断创建新归档。

预检包括数据库物理完整性（SQLite）、存储空间估算、旧版凭据能否由当前根密钥解密，以及已知新增对象与 Goose 版本是否一致。PostgreSQL/MySQL 原生快照本身也检查备份工具与读取权限；MySQL 仍要求 InnoDB。备份成功后，PostgreSQL 检查 schema 创建权限及 `grants` 所有权，MySQL 在保留命名空间 `__easyssh_migration_probe_` 下创建并清理临时检查用的持久表/存储过程，以验证实际 DDL/DML/例程权限（包含角色授权）。检查对象不承载业务数据；中断后下次预检清理这些对象。外部数据库服务器自身磁盘空间仍由数据库运维管理，本机空间估算不是配额预留。

SQLite 历史外键异常不会被擅自修复或直接忽略。迁移记录保存按逻辑主键、引用值、父表和约束生成的异常摘要及重复次数，升级后出现新增异常就阻止业务启动。使用逻辑主键避免 `VACUUM INTO` 重排行号造成误判；`WITHOUT ROWID` 表若存在历史异常，需先人工修复。对当前部署此前发现的历史异常，升级仅记录基线，不修改异常业务行。完整实例备份原有的严格校验策略不变。

### 中断与失败处理

每个数据库的数据目录保存 `.easyssh-migration-<数据库标识摘要>.json`，包含源/目标版本、脚本摘要、恢复点校验和、阶段和时间。完成后的报告另存于恢复点旁的 `.age.json`。状态写入通过临时文件、刷盘和原子替换完成。不得在未确认数据库状态时删除或手动改写这份记录，也不要修改已经发布的版本化 SQL。

SQLite/PostgreSQL 每个迁移文件及其 Goose 版本记录处于同一事务。失败只回滚当前步骤：例如未来 1 → 2 已完成、2 → 3 失败时会停在 2。重启确认脚本和结构一致、恢复点可用后从 2 继续，不重新备份。新增非事务迁移不能直接进入这条自动重试路径。

MySQL DDL 隐式提交。持久化记录显示已开始迁移、但尚未达到目标版本时，自动重启会停止，不盲目重复 DDL。先核对 Goose 版本、SQL 和实际结构；恢复为与已记录版本完全一致的结构后，可以显式执行：

```sh
./easyssh-api maintenance schema-upgrade --resume
```

`--resume` 仍检查结构、脚本摘要、恢复点和凭据，不会强行跳过已有的未记录表/字段。若状态无法确认，应提取升级前恢复点并恢复到新目标。普通 `maintenance schema-upgrade` 使用同一套备份及校验流程，不能绕过上述保护。所有维护命令须指向实际活动数据库与根密钥；使用启动器切换过副本的部署，要以启动器选择记录中的目标为准，不能默认 `.env` 仍指向活动实例。

失败会退出而不开放业务，日志保留阶段与恢复点路径。程序不会因迁移失败或后续应用启动故障自动执行 Down，也不会自动覆盖原数据库。升级成功后需要回到旧程序，应先停机，结合旧程序支持的 schema 和新增数据保留要求选择人工回退或恢复副本。

### 提取升级恢复点

此命令不连接或修改当前数据库，也不依赖服务能否启动。`--into` 必须是尚不存在的目录：

```sh
./easyssh-api maintenance migration-extract \
  --file /backups/migrations/schema-1-to-2-ID-TIMESTAMP.age \
  --root-key-file /secure/original-instance-root.key \
  --into /srv/easyssh-upgrade-recovery
```

密钥文件必须包含创建恢复点时的 Base64 实例根密钥；从 `ENCRYPTION_KEY` 或启动器选择所指向的密钥存储中安全取得，不把密钥内容放入命令参数或日志。提取结果是权限受限的明文快照和配置，应按敏感数据管理。

- SQLite：`database.dump` 是独立数据库文件，可在新目录中作为数据库使用，配合提取的 `root.key` 及原有传输存储。先停机、验证副本，再切换部署数据库配置；如由启动器管理，还必须按实例切换规则处理持久化选择，单改 `.env` 不会覆盖已选副本。
- PostgreSQL：使用 `pg_restore --single-transaction --no-owner --no-acl` 导入另建的空数据库。
- MySQL：使用匹配版本的原生客户端将 dump 导入另建的空数据库；导入失败保留原库，重新准备空目标，不在原库上反复导入。

确认后使用与恢复 schema 匹配的程序启动。若再次启动当前新程序，默认会重新向上迁移。恢复旧快照可能丢失快照之后的新数据，因此这里只提供提取入口，切换仍由操作者明确执行。

## 系统内置操作与历史

Web 和桌面端均提供创建、上传、下载、校验、恢复副本、删除、搜索和分页。创建、校验、恢复在后台执行，页面每 3 秒更新状态。备份密码仅存于当前任务内存，不写入历史或日志；每次校验和恢复重新输入密码。

历史记录使用备份目录中的独立 JSON 元数据，包含文件名、时间、大小、来源、状态、错误、版本、校验时间和恢复目录，不占用业务数据库。重启后中断任务标为失败或保留可用文件并显示中断原因。删除操作同时删除归档和历史，保留当前业务数据和已经恢复的副本；正在下载的归档不能删除。

- 服务端默认目录是数据目录旁的 `backups`，可通过 `EASYSSH_BACKUP_DIR` 指定。目录必须与业务数据目录和传输存储互不包含。
- 桌面端默认目录同样为数据目录旁的 `backups`，可通过 `EASYSSH_DESKTOP_BACKUP_DIR` 指定；上传和下载调用系统文件对话框。
- Docker 镜像使用 `/app/backups`；Compose 已增加独立持久化挂载（生产 `./backups`，开发 `./backups-dev`）。应用用户必须对挂载目录有写权限。
- 上传上限为 16 GiB，解压上限为 256 GiB；上传完成仅表示文件已保存，仍需密码校验。临时目录需要容纳解压数据。
- Web 下载使用限定到单个归档的一次性短期票据，由浏览器直接保存，不在页面内存缓存完整文件；下载端点仍检查 `backup:manage` 权限。

服务端备份期间阻止传输文件写入、删除和清理，以及传输存储配置变更；若已有传输或清理正在执行，本次任务显示原因，待任务结束后重新创建。数据库由原生快照提供事务一致性，其他不修改本地附件的服务可继续运行。桌面端收集快照时协调配置、通知、主机指纹文件和日志写入。外部工具修改文件或数据库不受应用锁控制。

**“校验”验证归档校验和、应用形态、数据库类型与版本要求；“恢复副本”才会实际恢复数据库并校验凭据。两者都不表示已切换当前实例。** 恢复副本写入 `backups/restored/<id>-<time>`，页面显示其目录；SQLite 可直接生成副本，PostgreSQL/MySQL 需预先配置 `EASYSSH_RESTORE_DSN` 指向新的空库。使用启动器的服务端磁盘 SQLite（本地运行、Docker）和桌面端可在恢复后单独确认“启用并重启”；外部数据库仍使用下文的手动配置切换流程。

### 服务端磁盘 SQLite：启用并重启

部署包含此功能的新前后端版本后，按原方式启动服务端程序一次即可。磁盘 SQLite 的正常入口自动作为启动器运行，再启动实际 HTTP 服务子进程；现有账号、数据库格式、备份文件和 API 不变。无需额外安装启动器，也不编辑 `.env`。外部数据库、SQLite URI 和内存数据库不启用此流程；需要完全绕过启动器时设置 `EASYSSH_INSTANCE_LAUNCHER=off`。

1. 在完整备份页面恢复副本，等待成功。
2. 点击该行“启用并重启”，核对备份名称和时间，确认连接中断及重新登录提示。
3. 启动器持久化切换意图，通知旧服务优雅退出，等待其数据库与目录锁释放。正在进行的备份、恢复及归档下载会阻止启用。
4. 启动所选目录，统一使用对应数据库、根密钥和原备份目录。完成数据库连接、凭据解密、服务初始化及 HTTP 端口绑定后才提交选择；任务队列在选择提交前不执行任务，通知工作线程也不会提前发送通知。
5. 页面进入无需旧登录会话的等待页，仅用随机操作标识查询结果。服务可访问并返回成功状态后，点击“重新登录”，使用备份中的账号核对数据。

新实例未通过上述启动校验时自动回到切换前实例。旧服务 60 秒内不能退出时终止其进程树并重新启动原实例，不继续启用副本；新服务启动校验最长等待 90 秒。程序或机器在切换意图提交后、选择确认前中断时，下次启动回到切换前实例。确认启用后的日常运行故障不触发自动来回切换。页面五分钟仍未取得结果时显示“未确认”，不会把单纯端口可达当成成功。

页面提供“切回上一实例”：保留两份数据目录，只切换启动选择，不把切换后的新数据合并回去。启用后原备份历史仍可见；备份存储检查仅对启动器选中的 `backups/restored/` 子目录放行，其他目录重叠仍被拒绝。不要移动已启用目录，其中传输文件引用仍使用恢复时的绝对路径。

启动器使用工作目录下的 `.easyssh-runtime/selection.json` 保存当前、上一实例和未完成的切换意图，通过写入临时文件再原子替换持久化。该目录还保存原实例的根密钥，Windows ACL 限制为运行账号、SYSTEM 和管理员，Unix 目录权限为 0700、文件为 0600；不要删除或提交到 Git。可通过 `EASYSSH_INSTANCE_STATE_DIR` 指定固定绝对路径，必须与数据库目录、备份目录分开。应固定启动工作目录和运行账号；更换可执行文件无需重置选择。已保存的实例选择优先于原 `.env` 的数据库与密钥配置；端口等其他部署配置继续从原环境读取。

应急手动切回：先停止启动器，再设置 `EASYSSH_INSTANCE_LAUNCHER=off`，使用原 `DB_DSN` 和原根密钥启动。原 `.env` 未被修改；若原来未显式配置密钥，原数据目录的 `easyssh-root.key` 仍保留。保留 `.easyssh-runtime` 可继续检查切换记录，排障前不要删除任一实例。完整备份恢复到其他机器仍按归档恢复流程执行，不需要复制本机启动器状态。

### Docker

Docker 镜像的启动入口使用 tini 回收进程；EasySSH 启动器接收停止信号并等待服务子进程退出。标准输出和错误输出均转发至容器日志。生产与开发 Compose 均增加独立命名卷保存 `/app/instance-state`，原数据和备份目录挂载保持不变。`stop_grace_period: 75s` 为优雅退出保留时间。

升级已有部署时需要同时更新镜像及 Compose 配置；首次启用副本前确认数据、备份、启动器状态三处都持久化，且容器账号能写入。不使用 Compose 时需自行给 `/app/instance-state` 挂载持久卷，并设置至少 75 秒的停止超时。不要删除状态卷或执行清除该卷的命令，否则重建后可能重新选择原环境中的数据库。根密钥与状态卷一同按敏感数据保护。容器健康检查在切换间隙可能暂时失败，外部探活管理器应给切换留出时间，避免打断回退。

### 桌面端：启用恢复副本

桌面端使用同一切换与回退状态机；点击“启用并重启”后窗口退出并重新打开，不进入 Web 登录等待页。候选数据库、凭据解密和所有 Wails 服务通过初始化、主窗口运行时就绪后才提交选择；前端启动入口等待提交完成，再挂载业务页面，任务历史清理也在提交后执行。不能仅凭应用事件循环启动就确认成功，因为此时 WebView2 可能仍在初始化。新窗口会提示成功或回退，备份页也保留最后结果和“切回上一实例”。正在进行的终端、传输和 AI 请求会中断。

默认启动器状态为原数据目录旁的 `.easyssh-desktop-runtime`，可以用 `EASYSSH_INSTANCE_STATE_DIR` 指定；该目录的 `launcher.log` 保存父进程启动与回退信息。桌面密钥始终保存在系统凭据库，不写入启动器文件或子进程环境。旧数据目录继续使用原凭据条目；每个新恢复副本使用独立凭据条目，目录内 `.easyssh-key-account` 仅保存条目标识。失败或回退不会覆盖原密钥；不要手工删除仍被副本引用的凭据条目。跨机器恢复应上传加密归档重新恢复，不能只复制数据目录及条目标识。

自动更新的独立帮助进程会等待桌面子进程和启动器均退出后再替换程序，重新启动时沿用持久化选择。手工应急启动可设 `EASYSSH_INSTANCE_LAUNCHER=off` 和 `EASYSSH_DESKTOP_DATA_DIR` 指向原目录；也可按下文维护命令恢复到新目录。禁用启动器后不显示一键启用入口。

命令行仍作为无法登录或系统无法启动时的应急入口，不依赖历史列表。旧的手工命令行归档不会自动出现在列表，可通过“上传已有备份”纳入管理。

## 服务端完整备份

1. 停止 EasySSH 服务，保留原有 `DB_DRIVER`、`DB_DSN`、`ENCRYPTION_KEY` 和数据目录配置。
2. 准备只允许操作者读取的密码文件，例如 `/secure/backup-password`。密码不放在命令参数中。
3. 将备份写入数据目录之外：

```sh
./easyssh-api maintenance backup \
  --file /backups/instance.easyssh.age \
  --password-file /secure/backup-password
```

命令检查数据库版本、凭据解密和 SQLite 完整性，创建原生快照，收集数据目录及配置的传输存储，然后流式生成 age 加密的 tar.gz 归档。源文件不允许是符号链接或特殊文件，避免生成缺失外部内容的备份。归档清单记录应用版本、数据库类型和版本、迁移版本、文件长度和 SHA-256。输出文件必须不存在。

SQLite 使用 `VACUUM INTO`，包含已提交的 WAL 内容。不会直接复制运行中的主数据库文件。PostgreSQL 使用 `pg_dump --format=custom`；MySQL 使用 `mysqldump --single-transaction`，要求业务表为 InnoDB。镜像包含 PostgreSQL 和 MariaDB 原生客户端；独立二进制部署需自行安装与数据库版本匹配的客户端。PostgreSQL 的 dump 客户端不能低于源服务端主版本。

MySQL 原生连接支持 unix socket、TCP 和驱动的 `tls=true/false/skip-verify/preferred` 设置；应用自定义注册的 TLS 配置不能自动转成原生客户端配置。MySQL 基线要求 MySQL 8.0.13+，使用表达式默认值；MariaDB 部署须按其版本验证相应 SQL 和客户端兼容性。

默认数据目录：SQLite 为数据库文件所在目录，PostgreSQL/MySQL 为 `EASYSSH_DATA_DIR`，未配置时为当前工作目录下的 `data`。备份根密钥使用应用实际加载的值，即使它来自 `ENCRYPTION_KEY` 环境变量也会加密保存。数据库连接口令不写进备份，恢复时由目标部署提供。反向代理、容器编排和外部服务配置仍由部署管理，不属于应用数据目录。

## 检查和恢复


```sh
./easyssh-api maintenance inspect \
  --file /backups/instance.easyssh.age \
  --password-file /secure/backup-password

./easyssh-api maintenance restore \
  --file /backups/instance.easyssh.age \
  --password-file /secure/backup-password \
  --into /srv/easyssh-restored
```

`inspect` 会解密、读取并核对所有文件。需要足够的临时磁盘空间；归档解压上限为 256 GiB。它验证归档完整性，不代替数据库恢复演练。

`restore` 要求 `--into` 不存在。流程如下：

1. 在权限受限的临时目录解密并核对清单，拒绝重复路径、路径穿越、符号链接和多余内容。
2. 检查应用版本及数据库版本。仅支持本次新基线及其后续版本的归档；服务端和桌面端各自判断版本，旧迁移链归档不兼容。
3. SQLite 恢复到临时数据库；PostgreSQL/MySQL 恢复到操作者提供的空数据库。
4. 后续出现增量迁移时，在隔离副本中升级受支持的备份到当前 schema。验证根密钥能够解密应用凭据，SQLite 另检查数据库与外键完整性。
5. 清理登录会话、自动化令牌、设备授权和短期认证请求，并撤销恢复出的资源授权，防止旧快照复活已撤销授权；保留资源及同步文档。传输文件路径调整为恢复目录内的 `transfers`。
6. 把恢复完成的文件发布到新目录，输出该目录。**不会自动替换原实例或启动服务。**

SQLite 切换时，将 `DB_DSN` 设置为 `/srv/easyssh-restored/easyssh.db`。保留旧目录，即可在停止新实例后切回。根密钥从恢复目录的 `easyssh-root.key` 读取；必须取消旧的 `ENCRYPTION_KEY` 覆盖，或确保它与恢复密钥完全相同。

PostgreSQL/MySQL 恢复前，创建独立空数据库，并通过 `EASYSSH_RESTORE_DSN` 环境变量提供相应的 Go 驱动 DSN。可以用 `--target-dsn-env OTHER_VARIABLE` 指定其他环境变量名。恢复后将正常服务的 `DB_DSN` 指向该数据库，将 `EASYSSH_DATA_DIR` 指向恢复目录，并使用恢复根密钥。原数据库保持保留。

PostgreSQL 的原生导入使用单事务；MySQL DDL 无法保证整体事务回滚。若 MySQL 导入失败，目标是隔离的新数据库，原实例不受影响；删除失败的临时目标库并重新创建空库后再重试。程序不会擅自清空数据库。

完整备份只在同一数据库类型、同一应用形态内恢复。服务端与桌面端之间的个人数据通过设备同步流转。SQLite、PostgreSQL、MySQL 之间的数据库类型转换需要另行制定迁移方案，当前产品不提供通用迁移入口。

## Docker

先准备宿主机备份目录和密码文件，确保容器中的应用用户有适当权限。在 `docker` 目录使用项目的 Compose 配置：

```sh
docker compose stop easyssh
docker compose run --rm --no-deps \
  -v /srv/backups:/backups \
  -v /srv/secrets/backup-password:/run/secrets/backup-password:ro \
  easyssh ./easyssh-api maintenance backup \
  --file /backups/instance.easyssh.age \
  --password-file /run/secrets/backup-password
docker compose start easyssh
```

恢复时将新的宿主机父目录挂载进维护容器，把 `--into` 指向该挂载下尚不存在的子目录。确认成功后再修改正常服务的数据卷或数据库连接。Compose 管理的现有数据卷不要在恢复命令中直接覆盖。

## 桌面端

完整退出应用（仅关闭窗口可能仍在托盘运行），使用桌面程序同样的子命令：

```sh
EasySSHDesktop maintenance backup --file /backups/desktop.easyssh.age --password-file /secure/backup-password
EasySSHDesktop maintenance inspect --file /backups/desktop.easyssh.age --password-file /secure/backup-password
EasySSHDesktop maintenance restore --file /backups/desktop.easyssh.age --password-file /secure/backup-password --into /new/desktop-data
```

Windows 使用实际的 `.exe` 路径；macOS 使用应用包内的可执行文件路径。命令在 Wails 和界面启动之前执行。

默认数据目录仍为可执行文件旁的 `data`；可通过 `EASYSSH_DESKTOP_DATA_DIR` 指定恢复目录。完整备份加密保存系统凭据库中的根密钥。恢复时会检查数据库凭据、同步对象和代理密码；恢复成功时为副本创建独立系统凭据条目，并保存条目标识；原实例密钥保持不变。已有旧数据目录不需要迁移凭据条目。恢复后的设备同步需要重新授权。

## 设备同步与数据边界

桌面端设备同步入口位于顶部设置菜单前的云图标。云图标只负责立即同步，不打开页面；未配置、已暂停或状态加载失败时禁用，并提示通过下拉菜单进入同步设置。已绑定并启用时，点击立即同步，原有自动同步继续运行。只有云图标旁下拉菜单中的“同步设置”打开设置页面，用于修改同步范围、加入本地数据、处理冲突，或退出绑定后更换服务端和账户。同步中显示进度图标，失败或冲突显示提示点。备份与恢复页面只管理完整备份，Web 与桌面共用页面布局。

桌面端填写服务端地址，通过浏览器登录并授权远端账户。多台桌面绑定同一账户后，通过服务端交换数据；Web 页面直接使用该账户的服务端数据。首次连接接收远端基础配置，现有本地配置不会自动上传。桌面新建的服务器和脚本也需要主动加入当前同步空间。

- 基础范围：本人服务器连接参数、名称、分组、标签、描述、自定义排序，以及个人脚本。共享资源不纳入同步。
- 可选范围：已同步服务器的密码和 SSH 私钥、个人 AI 配置与 API Key、AI 会话与历史。每个范围都需要设备授权，并在桌面单独开启。系统共享 AI Key 不参与同步。
- AI 会话：已有本地会话需手动加入；开启会话同步后，新建会话自动加入当前空间。同步包含消息、附件和历史工具结果，接收端以只读权限和空闲状态保存，不恢复运行中的终端连接或执行历史任务。
- 本地 AI 配置：通过“将本地 AI 配置复制到当前空间”主动加入；绑定账户不会自动用本地配置覆盖远端配置。
- 排序：新设备的空列表不产生排序修改；只因已删除服务器 ID 不同、实际顺序一致的历史不提示冲突。实际顺序不同的并发修改仍需选择版本。
- 冲突与删除：连接参数、脚本内容及排序有冲突时保留本端当前生效值；首次接收且有冲突的记录暂不加入业务列表。只有明确选择版本才应用冲突字段，其他字段正常同步。AI 会话可另存版本；删除会传播到其他设备。同步不能替代备份。
- 状态与授权：查看 Web 同步状态不会合并或写入同步数据。同一空间重新授权后，仅保留此前已开启且此次仍获授权的范围。
- 容量：单份同步历史上限为 32 MiB（Base64 编码后的文档）；交换请求上限 48 MiB，桌面接收上限 96 MiB。单条内容和附件限制保持不变，暂不自动压缩或清理历史。
- 数据副本：关闭同步范围或撤销设备授权只阻止后续同步，不会收回已经复制的数据。凭据与同步对象在两端加密存储，服务端能够解密处理，并非端到端加密。

完整备份用于同端整体恢复和迁机，包含对应实例持久化的 AI 历史；恢复后设备同步需要重新授权。Web 与桌面不能互相恢复完整归档。完全离线的跨端迁移、跨数据库类型迁移及通用 JSON 资源导入导出不属于当前产品能力。


## 迁移工具和命名规范

继续使用 `github.com/pressly/goose/v3`、嵌入式 SQL 和现有维护命令，不新增第二套迁移框架，不使用 GORM AutoMigrate。应用版本（例如 `2.0.0`）与数据库编号独立；只有数据库结构或持久化数据需要变化时才增加迁移。

| 项目 | 服务端 | 桌面端 |
| --- | --- | --- |
| 目录 | `server/internal/storage/schema/{sqlite,postgres,mysql}/` | `desktop/EasySSHDesktop/internal/storage/schema/sqlite/` |
| 初始化文件 | 每种数据库一个 `00001_initial.sql` | `00001_initial.sql` |
| 当前版本 | `schema.Version = 2` | `schema.Version = 1` |
| 后续编号 | 从 `00003` 连续递增 | 独立从 `00002` 连续递增 |

文件名固定为 `五位编号_lower_snake_case.sql`，例如 `00002_add_server_notes.sql`。名称以小写字母开头，后续单词使用小写字母或数字，单个下划线分隔。服务端同一变更必须提供三种数据库的同编号、同文件名脚本；不能只修改 SQLite。桌面端按自己的结构变更独立创建，不要求和服务端编号相同。

创建模板（仅写入源码文件，不连接数据库）：

```bash
node scripts/new-migration.mjs server add_server_notes
node scripts/new-migration.mjs desktop add_server_notes
# 等价入口：pnpm migration:new server add_server_notes
```

工具读取现有序列，拒绝缺号、重复描述和数据库间文件不一致，创建下一编号的全部脚本，并同步对应 `schema.go` 的 `Version`。模板的 `Up` / `Down` 尚无可执行 SQL，必须补全才可发布。`BaselineVersion` 固定为 1，不能随新迁移递增。

初始化只提供 `-- +goose Up`，直接创建当前完整结构，不包含旧库升级过程，也不提供删除整个基线的 Down。运行时不会回退到基线之前。后续迁移必须提供非空的 `-- +goose Up` 和 `-- +goose Down`，并说明数据损失及恢复点需求。SQLite/PostgreSQL 由 Goose 将每个方向和版本记录放在同一事务，失败回滚；MySQL 显式使用 `NO TRANSACTION`，DDL 隐式提交，数据修改需使用事务及异常回滚处理，DDL 中断从恢复点恢复，不能声称完整事务回滚。

**初始化基线发布后不可修改，所有已发布迁移禁止编辑、删除、重命名或重新编号。** 后续变更只能追加；还须同步更新 `CheckUpgradeSource` 的对应版本结构检查、备份/恢复校验和相关文档。不要通过修改 Goose 版本记录跳过迁移。发布工具会检查文件名、连续编号、三种数据库的一致性、Up/Down 内容以及历史发布脚本是否被改写。

服务端普通启动自动升级；离线维护仍使用：

```bash
./easyssh-api maintenance schema-upgrade
./easyssh-api maintenance schema-rollback
```

桌面端先退出应用，再显式运行维护命令，每次操作必须先创建加密完整备份：

```bash
EasySSHDesktop maintenance schema-upgrade --file /backup/before-upgrade.age --password-file /secure/backup-password
EasySSHDesktop maintenance schema-rollback --file /backup/before-rollback.age --password-file /secure/backup-password
```

当前服务端有 schema 1 → 2 增量迁移；`schema-rollback` 每次仅退一版，不能回退到初始化基线之前。schema 2 的 Down 只恢复空的 CSRF Origin 字段；恢复旧值需使用升级前备份。回退后使用匹配程序，避免新程序自动再次升级。

## 统一发布版本入口

继续使用 VS Code 的 Scripts: 版本号更新任务，或 `bash scripts/bump-version.sh <x.y.z>`。该入口不连接数据库、不执行 SQL、不安装依赖、不构建或运行测试；推送版本标签会触发现有 GitHub Actions 测试、构建和发布流程。

先提交业务代码与迁移，再更新应用版本。也可用 `node scripts/release-version.mjs --check` 只检查源码版本及迁移文件。应用版本更新会核对 Web、桌面和打包资产与 `VERSION` 一致；不含数据库变化的发布不增加 schema 编号。发布后由既有不可变迁移检查保护 SQL。

本次重置保留 `v2.0.0` 发版提交之前的应用版本；历史发布和标签清理后，下一次显式发版可使用 `bash scripts/bump-version.sh 2.0.0`。不要重新推送旧分支上的历史 `v2.0.0` 发版提交作为新发布基线。


## 跨端备份适用范围

服务端完整备份可以在本地服务端和 Docker 之间恢复，前提是数据库驱动相同并满足版本要求。桌面完整备份用于桌面端。Web 与桌面端的表结构、账号归属和密钥存储不同，不能直接互相恢复完整归档；一键启用没有改变此限制。跨端个人数据通过远端账户同步，服务器凭据、个人 AI 配置和 AI 历史需单独授权并开启对应范围。完整备份包含对应实例的 AI 历史；跨端流转不会搬运运行中的执行状态。
